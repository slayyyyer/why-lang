Install

From clone to a running page.

Why builds to one jar. Point it at a folder, open the URL, edit the file, refresh. There is no separate asset pipeline or database server to start.

Requirements

  • JDK 21 or newer — the language, server and build all target 21.
  • Maven 3.9+ — to build the shaded jar.

Check what you have:

terminal
java -version
mvn -version

Build and run

terminal
git clone https://github.com/slayyyyer/why-lang.git
cd why-lang
mvn package
java -jar target/why.jar ./site

The demo site starts on http://localhost:8080. If the port is taken, add --port 3000.

One jar. The SQLite JDBC driver is shaded in. There is no runtime dependency to install beyond the JDK.

A first page

Make a new folder inside the project and add index.why in an editor:

mysite/index.why
<h1>Hello from a file</h1>
<p>No build step, no route table.</p>

A file with no section labels is all view, so plain HTML is already a valid page. Start the server against that folder:

terminal
java -jar target/why.jar ./mysite --port 3000

Open http://localhost:3000/. Add about.why next to it and /about exists immediately. Copy a file in, refresh, it is live — every request re-reads and recompiles the page.

Options

OptionMeaning
siteFolder of .why files. Default: the current directory.
-p, --port NPort to listen on. Default: 8080.
--db FILESQLite file. Default: data.db inside the site folder.
check [site]Compile every page, report problems, print the page map, exit 1 on problems. Does not serve or touch the database.
-h, --helpUsage.

The database

If data.db is missing when the server starts and the site folder contains schema.sql, the script runs once. A small site can therefore be a folder you can copy anywhere.

mysite/schema.sql
create table if not exists notes (
  id integer primary key,
  body text not null,
  created_at text not null
);

There is no migration runner. In development, deleting the database and letting schema.sql recreate it is the whole story. In anything you care about, keep the schema and migrations outside Why.

Check a site

Before serving, or in CI, compile the whole folder:

terminal
java -jar target/why.jar check ./mysite

It reports unresolved imports and partials, duplicate defs, undefined free-function calls and URL collisions, then prints a page map. It exits 0 when clean and 1 when it finds something. It never opens the database.

The same jar has a check recipe for a CI workflow on the recipes page.

Running it somewhere

The artifact is target/why.jar plus your site folder. On a server, run it under whatever supervises processes, put it behind a reverse proxy if it is exposed, and keep backups of the SQLite file.

Not production-hardened. There is no TLS, authentication, rate limiting or sandbox. Pages can run arbitrary SQL and read the database. Run it on a trusted network, or treat it as a prototype.

Troubleshooting

“Address already in use”

Another process owns the port. Add --port 3000 or pick another number.

“cannot find import 'header'”

The import is a bare name. It looks for header.why next to the importing page, then in the site root. Check the spelling and the folder. A leading _ is allowed and means import-only.

/_header answers 404

That is the convention: files whose name starts with _ can be imported but are never served. Use {{> _header}} from a page.

I changed schema.sql and nothing happened

The script only runs when the database file is missing. For the demo, stop the server, delete site/data.db, and start again.

“java: command not found” or the wrong version

Install JDK 21+ and check java -version. The build also needs Maven on PATH.

The page is blank

Check the server log: compile and runtime errors are printed with file:line, and the browser gets a 500 page with the source excerpt. why check catches most problems before the request.
